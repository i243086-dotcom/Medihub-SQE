**Execution and scope.** OWASP ZAP 2.17.0 with Report Generation add-on 0.43.0 and Eclipse Temurin 21.0.13.1 ran in a temporary daemon session. The [launcher](../../../tools/phase4_passive.py) invokes Python 3.11.9 pytest 9.2.0 with `--browser chromium --self-contained-html --junitxml`, Playwright 1.65.2 and pytest-html 4.2.0. The passive queue drained to zero after the real patient POST and DELETE and all denial checks. The launcher then called `reports/action/generate` with `risk-confidence-html` and `traditional-json`. The HTML export selects native alert and summary sections and leaves out raw HTTP headers and bodies. Both exports are unchanged tool output. The original custom HTML remains historical and supplementary. [ZAP Report Generation API](https://www.zaproxy.org/docs/desktop/addons/report-generation/api/)

**Counting.** The daemon observed 142 messages versus 141 previously. The only extra method, URI and status combination was one successful GET of `/api/patient/history`. The alert API returned the same 61 records and 10 unique rule IDs as the historical capture. The official HTML summarizes 10 alert types, three Medium, three Low and four Informational. The official JSON lists 23 exported instances, five Medium, ten Low and eight Informational. ZAP's report alert tree represents systemic and repeated alerts differently from the alert-history API. The 38-record difference consists of Server header disclosure (25 API instances versus 4 exported, systemic), missing nosniff (20 versus 5, systemic), and authentication request identification (3 versus 1 on the same login operation). [ZAP alert deduplication](https://www.zaproxy.org/blog/2025-09-30-alert-de-duplication/) · [Historical capture](../zap-run.json)

**Test correction.** The first rerun timed out in the doctor test after Flask had already returned HTTP 200. The appointments fetch starts at login and the original listener was installed afterward. The corrected test observes the response during login, then verifies the rendered assigned row and both SQLite records. The application source stayed identical. The two subsequent eight-test sessions passed.

**Dependency audit.** pip-audit 2.10.1 used the PyPI service, `--path` against the actual MediHub venv, `--format json` and `--desc off`. It returned exit 1 for findings. Results match the historical count of 99 packages, no skips, 103 advisory records across five packages and 71 per-package advisory groups after alias deduplication. The [historical advisory table](../dependency-advisories.html) is a supplementary readable index. The production deployment and advisory reachability remain unassessed.

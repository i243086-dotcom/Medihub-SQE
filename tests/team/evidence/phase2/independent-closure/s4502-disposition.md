[GitHub evidence](github-before.json) · [Shaheer's assessment](https://github.com/i243086-dotcom/Medihub-SQE/pull/11#issuecomment-7165956390) · [Momin's assessment](https://github.com/i243086-dotcom/Medihub-SQE/pull/11#issuecomment-7166317600)

The finding is at Flask application construction in `backend/app.py`. JWT is accepted from the `Authorization` header, and the role decorators verify it before protected handlers run. All 14 protected write routes returned 401 for a valid JWT cookie alone and 403 for a wrong-role bearer header alongside that cookie. The rejected calls left SQLite data unchanged. Login returns a bearer token in JSON, registration starts no authenticated session, and logout sets no cookie. Five preflights returned neither an allow-origin nor an allow-credentials header. The frontend explicitly attaches the bearer token to its relative API requests. The signed-ID changes affect appointment lookups only. ## Manual procedure when the owner chooses to resolve it

1. In the signed-in SonarQube session, open **MediHub Phase 2 Candidate**, then **Issues**. Filter by `python:S4502` and open the finding in `backend/app.py` at Flask construction. Confirm the issue's source, scanner revision and deployment assumptions. [Dashboard](http://127.0.0.1:9001/dashboard?id=medihub-phase2-candidate)
2. With **Administer Issues** permission, select the issue's **Open** status and choose **False positive**. Enter the justification below and select **Resolve**. Ask the project administrator to perform this step if the option is unavailable. [SonarQube issue documentation](https://docs.sonarsource.com/sonarqube-community-build/user-guide/issues/managing#marking-an-issue-as-false-positive)
3. Capture the issue history and updated metrics with the analysis revision. Recheck security A and the other required thresholds before changing the release decision.

> False positive for the reviewed header-only JWT configuration. Protected MediHub writes require an explicit Authorization: Bearer header and role verification. A valid JWT cookie alone is rejected on all 14 protected write routes. Login returns JSON without an authenticated cookie, registration starts no session, and logout sets no cookie. Five cross-origin preflights granted neither origin nor credential sharing. Shaheer and Momin independently reviewed this evidence on PR #11 at fde115c. Reassess if a deployment proxy adds cookie authentication, changes CORS, or another route accepts ambient credentials.

## GitHub Actions

The workflow measures every PR merge candidate on a fresh loopback SonarQube instance. It scans the actual target revision first so the candidate has an auditable new-code baseline. It exports the S4502 finding from that instance and enforces the native gate plus the entire-project thresholds. The workflow performs no issue transition. A local false-positive status stays in the local database. If the owner later authorizes making the reviewed disposition portable, a persistent CI SonarQube project with human review of its exact issue is the preferred option. Any replay into a disposable scanner needs separate approval and must verify the rule, component, issue hash, reviewed source and review state before transition. Recheck the measured Sonar rating and native gate after any transition.
